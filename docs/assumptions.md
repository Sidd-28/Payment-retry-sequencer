# Phase 1 — Synthetic Data Generation: Assumptions & Calibration Notes

This documents every assumption baked into `generate_payment_data.py`, split into
(1) things calibrated against a public source, (2) things I could not find a public
number for and had to assume, (3) places where I deviated from or extended the
schema as written, and (4) simplifications in the simulation itself.

## 1. What's calibrated against a public source

| Assumption | Value used | Source |
|---|---|---|
| UPI system-wide **technical decline** rate (bank/NPCI-side failures: timeouts, server errors) | ~0.7–0.8%, down from 8–10% in 2016 | NPCI MD Dilip Asbe, SBI Banking & Economics Conclave, Nov 2024 (reported by multiple outlets, e.g. Paytm's summary of the remarks) |
| UPI **business decline** target (user-side: wrong PIN, insufficient balance, etc.) | target <5% (technical decline target <1%) | NPCI Circular OC-149 (June 2022), as cited in industry benchmarking writeups |
| Merchant-side blended UPI success rate | 92–96% typical, <90% considered a problem | Same OC-149-referencing source |
| UPI failures cluster at **month-end** (last 3–5 days) — salary credits, EMI debits, advance-tax dates hitting bank servers simultaneously | Modeled as a 4-day "month-end" window with a 1.6× failure multiplier | Public commentary on UPI failure patterns (merchant-facing gateway blog, 2026) |
| UPI failures spike **10 PM–midnight** due to scheduled/batch bank-side processing | Modeled as a 1.8× multiplier in that window | Same source as above |
| First business day after a holiday sees a pent-up-demand failure bump | Simplified to "every Monday morning" rather than an actual holiday calendar, 1.3× multiplier | Same source as above (conceptually) — the exact "first day after holiday" logic was simplified, see §4 |
| Card decline code **51 = insufficient funds** is the most common code; **54 = expired card**; **91 = issuer unavailable** is described as a "soft" decline that often succeeds on retry; codes in the 05/07/41/59 family relate to fraud/risk holds | Used as the basis for the `card` raw-code pools per `decline_reason_category` | Common ISO 8583-style decline-code reference used by payment gateways (e.g. PhonePe for Business's decline-code guide) |
| Recurring/subscription card payments in India face additional friction from RBI's e-mandate / Additional Factor Authentication (AFA) rules, and this disproportionately affects `invalid_otp`-style failures on recurring transactions | Reflected qualitatively (recurring payments get `invalid_otp`-eligible failures in the same proportions as everything else — see §2, I did **not** find a number to further inflate it by) | RBI e-mandate/AFA directives, as summarized by Stripe and 2Checkout/Verifone merchant documentation |

## 2. Assumed, with no public source found (flagged so you can defend or replace them)

- **Overall card decline rate in India (domestic, all reasons combined): ~10%.** I could not find a publicly disaggregated domestic figure (public reporting on Indian card declines focuses heavily on *international/cross-border* transactions, where aggressive risk auto-declines are well documented, e.g. RBI fraud-report-driven commentary from Razorpay). 10% is my estimate positioned above UPI's blended failure rate, reflecting that cards carry more expiry/limit/3DS friction than UPI. **Treat this as the weakest-sourced number in the config and the first one to revisit if you get real data.**
- **Netbanking (~9%) and wallet (~4%) overall decline rates** — no public aggregate found; set netbanking slightly below cards (redirect/timeout-prone but no card-expiry failure mode) and wallets lowest (closed-loop, fewer external dependencies), which matches general industry commentary but isn't citation-backed.
- **The full per-method breakdown of decline reasons** (e.g., "35% of failed UPI transactions are `insufficient_funds`") is my own allocation, informed by the *relative* ordering implied by the sources above (insufficient funds and OTP/PIN errors dominate business declines; timeouts/server errors dominate technical declines) but not a cited percentage split.
- **Salary-credit days used for `insufficient_funds` recoverability** (`[1, 2, 3, 7]` of the month) — a reasonable proxy for common Indian payroll cycles, not sourced to a survey.
- **Gateway "bad day" probability (3% per gateway per day)** and its 2× failure multiplier — invented to create gateway-specific degradation signal for `alt_gateway_retry` vs `same_gateway_retry` ground truth; there's no public SLA data behind this number.
- **Maintenance windows** (`gateway_b` 2–4 AM, `gateway_c` 3–4 AM) with a 5× multiplier — illustrative; real gateways don't publish maintenance-window failure multipliers.
- **Naive/historical retry probabilities and delay ranges** (the `naive_retry` config block) — these model what an *unmanaged* system does today (some blind retrying at arbitrary delays, including retrying `risk_block`/`card_expired` sometimes). Entirely assumption-driven, meant to create a believable "before" baseline for Phase 4's backtest against the ideal policy — not meant to represent any specific real system.
- **Recurring/subscription billing runs are clustered overnight (1–4 AM)** — a common real-world pattern (batch billing), but the specific hour-weight distribution I used is illustrative, not measured.
- **Merchant archetype amount distributions, payment-method mixes, and volumes** are directional (e.g., SaaS = narrow fixed-tier amounts, high `is_recurring`; marketplace = widest amount spread and most even payment-method mix) but the exact numbers (lognormal parameters, mix percentages) are my construction, not fitted to real merchant data.

## 3. Deviations from / extensions to the schema as written

- **`decline_reason_category` is null on successful attempts.** The schema marks it "required," but its own enum has no "success" value — there's no way to satisfy "required" and "the taxonomy of decline reasons" simultaneously on a row that didn't decline. I generate both successes and failures (attempt chains need both to be meaningful), so I treat the field as *required when the attempt failed, null when it succeeded*, and flag this explicitly rather than silently inventing a non-taxonomy value. Worth a one-line clarification in your schema doc.
- **`retry_action_taken`, `retry_outcome`, `time_to_recovery` are left `null` on every row.** Per the schema, these belong to the Phase 3 policy engine and are "null until evaluated" — Phase 1 data is pre-policy history, so populating them here would be putting Phase 3's output into Phase 1's input.
- **Added `payment_session_id`** (not in the canonical schema) to group an attempt chain — the schema has `previous_attempts` for history but no explicit key linking retries of the same underlying payment together. I needed one to build chains; you may want to formalize it (or an equivalent) in `schema.json`.
- **Added `merchant_archetype`** — purely for stratified analysis in later phases; safe to drop before feeding a model.
- **Added four `ctx_*` diagnostic columns** (`ctx_is_month_end`, `ctx_is_late_night`, `ctx_is_maintenance_window`, `ctx_gateway_degraded_day`) — expose the "why" behind a given decline probability for debugging/EDA. These are derived from timestamp + gateway and are *not* leakage (a real system would know the current time and whether its own gateway is degraded), but I'd still keep them out of Phase 2's feature set unless you deliberately want to test whether the classifier benefits from them.
- **Added five `gt_*` ground-truth columns** (`gt_is_recoverable`, `gt_ideal_retry_action`, `gt_ideal_time_to_recovery_seconds`, `gt_ideal_timing_hint`, `gt_requires_customer_action`) exactly as requested in point 5 — populated only for failed attempts, computed by an oracle that knows the true `decline_reason_category` and the true context. **These must never be used as classifier input features** — they leak the label the classifier is supposed to predict, and in production a real system wouldn't have them at decision time. They exist solely for Phase 4 backtesting (comparing an ideal policy's outcomes against the "naive retry" behavior actually recorded in the attempt chains).
- **Retry-action taxonomy gap for `invalid_otp`.** Your `decline_reason_category` table says `invalid_otp` is retryable "via a fresh customer-initiated attempt, not silent auto-retry," but your `retry-action taxonomy` table doesn't list an action for it — none of `same_gateway_retry` / `alt_gateway_retry` / `alt_payment_method_prompt` / `delayed_retry` / `no_retry` is scoped to cover it. Rather than silently picking one, I mapped it to `same_gateway_retry` **and** added `gt_requires_customer_action = True` on those rows so you can distinguish "auto-retry the same gateway" from "prompt the customer to try again." You'll probably want either a new action value (e.g. `customer_prompted_retry`) or an explicit note that `same_gateway_retry` covers both silent and customer-initiated cases, enforced by a separate flag — worth resolving before Phase 3 encodes a hard rule around it.

## 4. Simplifications in the simulation itself

- **Each retry attempt draws a fresh, independent decline probability** rather than deterministically simulating account balance / OTP-entry / gateway state. This means, e.g., a naive retry of an `insufficient_funds` failure *can* succeed even before the modeled salary date — representing the real-world fact that account state isn't perfectly predictable from a salary-day heuristic alone. The one deliberate exception: **`card_expired` and `risk_block` are "sticky"** — once an attempt chain hits either, every subsequent attempt in that chain is forced to fail with the same category. A card doesn't un-expire and a risk hold doesn't lift within a retry window, and I wanted the dataset to visibly punish "just retry it again" behavior for these two categories, since that's the whole point of the hard no-retry rule.
- **"First business day after a holiday" is approximated as every Monday morning**, not a real Indian bank-holiday calendar. If you want this more realistic, swap in an actual holiday list and gate the multiplier on `day after holiday` instead of `day == Monday`.
- **Festival-day spikes (Diwali, etc.) are not modeled** — the source material mentions them, but I left them out of the default config rather than inventing specific dates/multipliers with no real backing. This would be an easy, well-motivated addition if you want it (add a `festival_dates` list + multiplier to `time_effects`).
- **Raw `bank_response_code` values are synthetic placeholders**, not a verified real NPCI or bank code list — issuers and gateways don't publish one canonical list, and codes genuinely vary bank-to-bank in production, which is part of why the signal is "noisy" by design. The `card` pool loosely mirrors commonly-documented ISO 8583-style codes (see §1); the UPI/netbanking/wallet pools use an invented but internally consistent naming scheme. **Do not present these as real NPCI codes in your README** — present them as "illustrative noisy codes with a documented generation scheme," which is what they are.
- **8% of the time, a raw `bank_response_code` is sampled from the wrong category's code pool** (`response_code_noise_prob` in config) — this is the deliberate signal-noise the classifier (Phase 2) has to overcome, per your design notes. It's a flat 8% across all methods/categories; there's no evidence-based reason it couldn't vary by method.
- **Default dataset size (~63k attempt rows over Q1 2025, 8 merchants) is deliberately modest** for fast iteration. Every volume knob lives in `CONFIG["merchant_archetypes"][...]["daily_volume_range"]` — scale those up (and widen the date range) to generate a larger corpus; runtime is roughly linear in row count (a plain Python loop, not vectorized, in favor of keeping the retry-chain logic readable).

## 5. Reproducibility

Everything is driven by a single `numpy.random.default_rng(CONFIG["seed"])`, seed `42` by default. Re-running with the same `CONFIG` produces an identical dataset; changing `CONFIG["seed"]` alone gives you an independent draw from the same assumptions, useful for checking whether downstream results (Phase 2 classifier accuracy, Phase 4 backtest lift) are sensitive to the specific random draw versus the underlying assumptions.
